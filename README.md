# Конфигурационное управление
## Чаплина София Константиновна. ИКБО-21-24. Вариант №28

## Цель работы

Разработать инструмент визуализации графа зависимостей для менеджера 
пакетов. Готовые средства (менеджеры пакетов, библиотеки) для получения 
зависимостей использовать нельзя. 

## Структура проекта

Проект состоит из пяти этапов разработки, каждый из которых реализован в отдельном файле:

- step_1.py — минимальный прототип с конфигурацией
- step_2.py — сбор данных о зависимостях
- step_3.py — построение графа зависимостей с основными операциями
- step_4.py — дополнительные операции над графом (обратные зависимости)
- step_5.py — визуализация графа зависимостей

Вспомогательные файлы:

- test_repo_linear.txt — тестовый репозиторий с линейной структурой зависимостей
- test_repo_cycle.txt — тестовый репозиторий с циклическими зависимостями
- test_repo_complex.txt — тестовый репозиторий с комплексной структурой

## ЭТАП 1: МИНИМАЛЬНЫЙ ПРОТОТИП С КОНФИГУРАЦИЕЙ

### Требования этапа

1. Источником настраиваемых пользователем параметров являются опции 
командной строки. 
2. К настраиваемым параметрам относятся:
- Имя анализируемого пакета.
- URL-адрес репозитория или путь к файлу тестового репозитория.
- Режим работы с тестовым репозиторием.
- Версия пакета.
- Имя сгенерированного файла с изображением графа.
- Режим вывода зависимостей в формате ASCII-дерева.
- Максимальная глубина анализа зависимостей.
- Подстрока для фильтрации пакетов.
3. (только для этого этапа) При запуске приложения вывести все параметры, 
настраиваемые пользователем, в формате ключ-значение.
4. Реализовать и продемонстрировать обработку ошибок для всех параметров. 
5. Результат выполнения этапа сохранить в репозиторий стандартно 
оформленным коммитом. 

### Реализация

Этап реализован в файле step_1.py, содержащем следующие основные компоненты:

- parse_args(argv) — функция парсинга аргументов командной строки с использованием модуля argparse
- validate_args(args) — функция валидации всех полученных параметров с проверкой корректности и выводом ошибок
- print_params(args) — функция вывода всех параметров в формате "ключ=значение", отсортированных по имени ключа

Поддерживаемые опции командной строки:

- --package, -p (обязательна) — имя анализируемого пакета
- --repo, -r (обязательна) — URL репозитория или путь к файлу
- --test (флаг) — использовать тестовый репозиторий
- --pkg-version (по умолчанию "latest") — версия пакета
- --out, -o (по умолчанию "graph.png") — имя выходного файла
- --ascii (флаг) — вывести ASCII-дерево
- --max-depth (по умолчанию 0, что означает без ограничения) — максимальная глубина анализа
- --filter (по умолчанию пусто) — подстрока для фильтрации пакетов

## ЭТАП 2: СБОР ДАННЫХ

### Требования этапа

1. Использовать формат пакетов JavaScript (npm). 
2. Информацию необходимо получить для заданной пользователем версии 
пакета.
3. Извлечь информацию о прямых зависимостях заданного пользователем 
пакета, используя URL-адрес репозитория. 
4. (только для этого этапа) Вывести на экран все прямые зависимости 
заданного пользователем пакета. 
5. Результат выполнения этапа сохранить в репозиторий стандартно 
оформленным коммитом. 

### Реализация

Этап реализован в файле step_2.py и использует только встроенные модули Python (urllib, json, sys, os), что обеспечивает отсутствие зависимостей от менеджеров пакетов или сторонних библиотек.

Основные компоненты:

- fetch_package_metadata(package_name, version='latest') — функция для получения полных метаданных пакета из npm registry по адресу https://registry.npmjs.org/{package_name}
- get_direct_dependencies(package_name, version='latest') — функция для извлечения прямых зависимостей конкретной версии пакета
- parse_version(version_str) — вспомогательная функция для парсинга и сравнения версий
- print_dependencies(dependencies_dict, package_name, version) — функция для форматированного вывода зависимостей

Методология получения данных:

1. Отправляется HTTP запрос к npm registry (https://registry.npmjs.org/{package_name})
2. Полученный JSON парсируется и извлекается информация о версиях
3. Если пользователь запросил версию "latest", она разрешается через поле "dist-tags" в метаданных
4. Из информации о конкретной версии извлекается поле "dependencies", содержащее все прямые зависимости
5. Результаты выводятся в формате "имя@версия"

## ЭТАП 3: ОСНОВНЫЕ ОПЕРАЦИИ

### Требования этапа

1. Получение графа зависимостей реализовать алгоритмом DFS без рекурсии. 
2. Проводить анализ с учетом максимальной глубины, заданной 
пользователем. 
3. Не учитывать при анализе пакеты, имя которых содержит заданную 
пользователем подстроку. 
4. Корректно обработать случаи наличия циклических зависимостей. 
5. Поддержать режим тестирования. Вместо URL реального репозитория, дать 
возможность пользователю указать путь к файлу описания графа 
репозитория, где пакеты называются большими латинскими буквами. 
Продемонстрировать функциональность этого этапа на различных случаях 
работы с тестовым репозиторием. 
6. Результат выполнения этапа сохранить в репозиторий стандартно 
оформленным коммитом.


### Реализация

Этап реализован в файле step_3.py и содержит следующие ключевые компоненты:

- read_test_repository(file_path) — функция для чтения и парсинга тестового репозитория из текстового файла
- get_all_dependencies(...) — основная функция получения всех зависимостей (прямых и транзитивных)
- _get_all_dependencies_test(...) — реализация DFS без рекурсии для тестового режима
- _get_all_dependencies_npm(...) — реализация DFS без рекурсии для реального npm registry
- build_dependency_graph(...) — построение полного графа с применением фильтров
- print_dependency_graph(...) — форматированный вывод результатов

## ЭТАП 4: ДОПОЛНИТЕЛЬНЫЕ ОПЕРАЦИИ

### Требования этапа

1. (только для этого этапа) Поддержать режим вывода на экран обратных 
зависимостей для заданного пакета. Это те пакеты, которые зависят от 
данного пакета. Использовать алгоритм обхода из предыдущего этапа. 
2. Продемонстрировать функциональность этого этапа на различных случаях 
работы с тестовым репозиторием. 
3. Результат выполнения этапа сохранить в репозиторий стандартно 
оформленным коммитом.

### Реализация

Этап реализован в файле step_4.py и расширяет функциональность step_3.py. Основные компоненты:

- build_reverse_dependency_graph(...) — функция для построения графа обратных зависимостей
- _get_all_reverse_dependencies(...) — реализация DFS без рекурсии на инвертированном графе
- print_reverse_dependencies(...) — форматированный вывод обратных зависимостей
- add_reverse_mode_to_args() — расширенный парсер аргументов с поддержкой флага --reverse

Методология определения обратных зависимостей:

1. На основе исходного графа строится инвертированный граф, где reverse_graph[A] содержит список всех пакетов, которые зависят от A
2. Выполняется DFS без рекурсии (с использованием стека) на инвертированном графе, начиная от целевого пакета
3. Результат показывает все пакеты, которые (прямо или транзитивно) зависят от целевого пакета

## ЭТАП 5: ВИЗУАЛИЗАЦИЯ

### Требования этапа

1. Сформировать текстовое представление графа зависимостей на языке 
диаграмм Mermaid. 
2. Сохранить изображение графа в файле формата PNG. 
3. Если задан соответствующий параметр, вывести на экран зависимости в 
виде ASCII-дерева. 
4. Продемонстрировать примеры визуализации зависимостей для трех 
различных пакетов. 
5. Сравнить результаты с выводом штатных инструментов визуализации для 
выбранного менеджера пакетов. Если есть расхождения в результатах, 
объяснить их наличие. 
6. Результат выполнения этапа сохранить в репозиторий стандартно 
оформленным коммитом.

### Реализация

Этап реализован в файле step_5.py и содержит следующие основные компоненты:

- generate_mermaid_graph(...) — генерация текстового представления графа в формате Mermaid (язык диаграмм)
- save_mermaid_as_png(...) — сохранение диаграммы Mermaid в формате PNG с использованием сервиса kroki.io
- save_mermaid_text(...) — сохранение текста диаграммы Mermaid в файл с расширением .mmd
- generate_ascii_tree(...) — создание ASCII-представления дерева зависимостей с использованием символов box-drawing
- main(...) — главная функция этапа, координирующая все операции

### Сравнение с штатными инструментами

Сравнение с npm ls:

Команда npm ls показывает установленные локально пакеты и их версии в node_modules. Наш инструмент анализирует декларированные зависимости в npm registry, что позволяет:

- Получить информацию о зависимостях без необходимости установки пакета
- Анализировать зависимости удаленно
- Применять фильтры глубины и подстроки

Сравнение с npm view:

Команда npm view показывает только прямые зависимости пакета. Наш инструмент дополнительно:

- Строит полный граф транзитивных зависимостей
- Вычисляет обратные зависимости
- Применяет фильтры и ограничения
- Создает визуальное представление (Mermaid, ASCII, PNG)

Сравнение с npm-check-updates:

npm-check-updates используется для проверки доступности обновлений. Наш инструмент ориентирован на анализ и визуализацию структуры зависимостей.
